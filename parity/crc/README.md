# parity/crc/: golden fixtures for `crc_sdk.parametric`

The parametric insurance module `crc_sdk.parametric` is built in the fork `marc272/crc-sdk`. It never imports this repository's core, `parametric_insurance_design`. Where the two overlap, its results must match the core's, and the cases in `cases/` say what the core computes. The module's tests read them: the metrics (R-17, MAR-247), the design (R-16, MAR-248) and, later, the joint designs (R-21, MAR-45). This page describes the format, so that those tests can read the cases without our code.

- One case is one JSON document, `cases/<case_id>.json`. 39 cases, about 640 kB in total.
- The format is the parity contract of ADR 0005 §8. ADR 0005 is a draft (Proposed, MAR-244). If the accepted ADR renames a field, the rename is made in one place, the `_Fields` class of the script, and the cases are regenerated.
- The script is `parity/scripts/export_crc_fixtures.py` (MAR-245). The test is `parity/tests/test_crc_fixtures.py`.

## Regenerate and check

From the repository root:

```bash
uv run python parity/scripts/export_crc_fixtures.py            # rewrite cases/
uv run python parity/scripts/export_crc_fixtures.py --check    # compare, write nothing
uv run python parity/scripts/export_crc_fixtures.py --summary  # rewrite, print the case table
uv run pytest parity/tests/test_crc_fixtures.py                # what CI runs
```

The script takes under 10 seconds. CI runs the test in the parity step (`pytest parity/tests`). It regenerates every case in memory and judges the committed file against it:

- Everything but floats must be equal, except `generator.commit`. That includes `unique`, `unidentified` and `compare_parameters`.
- Floats must agree within 1e-6 relative for the values a solve produces (the `expected` block of a design case), and within 1e-12 relative elsewhere. The absolute floor is the same tolerance times the case's scale (below).
- In every design case, the core evaluates `expected.parameters` again. The objective value, the premium and every metric must agree with the committed ones within 1e-12.
- The committed levels must be an optimal design of the regenerated problem. They meet every constraint (bounds, monotonicity, cap, budget), their objective agrees with the regenerated optimum within 1e-6, and in LP cases they lie within the regenerated ranges, widened by 1e-6 of the scale.
- Only a unique design (`"exact"`) also has its identified levels, premium and metrics compared with the regenerated ones. A non-unique design's are one solver's point of the optimal set; a solver on another platform can return another point, so they are not compared. Unidentified levels are never compared.

So a change to the core's formulas, the data or the script that moves a value fails CI until the cases are regenerated. On one machine the regeneration is byte-identical. On another platform, a solver can return another point of the same optimal set, and the check above still holds. The test checks this with a regeneration under perturbed solvers (Clarabel without equilibration, HiGHS's primal simplex): it moves the solver's point in 13 cases and passes.

The test also reads every case the way the module's tests do, with plain numpy and the rules on this page only. It recomputes the payouts of the written cover, the objective value, the premium, the budget, the constraints and the plain metrics, and compares them with `expected`.

## The document

| Field | Value | Meaning |
|---|---|---|
| `case_id` | string | `<payout>-<objective or "fixed">-<pricing>-<scope>-<data>`, and the file name without `.json`. The payout is `step`, `linear-upper` or `linear-lower` |
| `kind` | `"design"` or `"evaluate"` | Design the cover from the template, or evaluate a fixed cover |
| `source` | `"core"` or `"closed_form"` | Who computed `expected`: the core, or this script from the closed forms of ADR 0005 §3 and §6 |
| `sample` | object | The outcome sample (ADR 0005 §4.1) |
| `cover` | object; a list of objects in joint cases | The cover document (ADR 0005 §3) |
| `objective` | object or null | null in evaluate cases |
| `pricing` | object | The pricing of the premium |
| `budget` | object or null | null in evaluate cases |
| `limit` | null | Always null here: the core's cap is the `Free` upper bound (below) |
| `scope` | `"individual"` or `"joint"` | One asset; or several assets and an objective on their sum (Phase 2, R-21) |
| `expected` | object | The values the module must reproduce |
| `compare_parameters` | `"exact"`, `"within_ranges"` or `"none"` | How a design's parameters are compared |
| `tolerances` | object | `objective_value`, `premium`, `metrics`, `parameters`: 1e-6 each |
| `generator` | object | `script`, `core_version` (the core's version) and `commit` |

### `sample`

- `asset_ids`: one asset in individual cases, three in joint cases.
- `period`: integer year labels, strictly increasing. One draw is one year.
- `probability`: `1 / n` for each of the `n` draws.
- `index`, `loss`: `n` rows with one value per asset, in `asset_ids` order. `numpy.asarray(sample["index"])` has the shape `(n, n_assets)` of ADR 0005 §4.1.
- `index_unit`, `loss_unit`. The loss unit is the cover's `payout_unit`.
- A year without an event has index 0 and loss 0. That is below every cover's first threshold, so no cover pays in it.

### `cover`

The cover document of ADR 0005 §3: `asset_id`, `index` (the index definition), `payout`, `payout_unit`, `schema_version` `"1.0"` and `semantics_version` `"crc-parametric-cover/1"`.

- Step payouts (`"kind": "step"`): `breakpoints` b_0 < … < b_{n−1} in index units, `levels`, `monotone` true, `tail` `"upper"`. A draw with index x gets level k for b_k ≤ x < b_{k+1}, the last level for x ≥ b_{n−1}, and nothing below b_0. The core's step payout has one more edge, b_n; values at or above it fall into the last bin too, so it changes no payout and is left out.
- Linear payouts (`"kind": "linear"`): `attachment`, `exhaustion`, `limit`, `tail`. The payout is `limit · clip((s − a) / (e − a), 0, 1)` on the severity s = x (upper tail) or s = −x (lower tail), with the thresholds mapped the same way. In the lower-tail case the thresholds decrease in index units: attachment −1, exhaustion −3.
- In design cases every level is a template marker, `{"free": {"grid": null, "lower": 0.0, "upper": <cap>}}`. The cap is the asset's largest loss on the sample. The core caps every level at it, so the module solves the same problem with `Free(lower=0, upper=cap)` and no `Limit`.
- In evaluate cases the levels and thresholds are numbers.
- Joint cases have one cover per asset, as a list in `asset_ids` order.

### `objective`, `pricing`, `budget`

- `objective`: `{"kind": "mse"}`, `{"kind": "expected_uncovered"}` or `{"kind": "weighted_cvar", "alpha": 0.9, "beta": β}`, with ADR 0005 §5.1's definitions over the draws.
- `pricing`: `{"kind": "pure"}` (P = E[π]) or `{"kind": "cost_of_capital", "rate": r, "q": q}` (P = (1 − r)·E[π] + r·CVaR_q(π)).
- `budget`: `{"ratio": 0.8}`: the premium is at most 0.8·E[L] on the sample.

In a joint case the objective, the premium and the budget are on the sums over the assets of the loss and of the payout of each draw.

### `expected`

| Field | Design cases | Evaluate cases |
|---|---|---|
| `objective_value` | The objective at `parameters`, on the sample | null |
| `premium` | The premium of the cover at `parameters`, on the sample, with `pricing` (the design premium) | The premium of the fixed cover, on the sample, with `pricing` |
| `parameters` | The core's solution: `{"levels[0]": …, …}`; in joint cases `{<asset id>: {…}, …}` | null |
| `unidentified` | The levels whose bin holds no draw of the sample: `["levels[6]"]`; in joint cases `{<asset id>: […], …}` | null |
| `unique` | Whether the identified levels of the optimum are unique (below) | null |
| `metrics` | Column → value (below) | Column → value |

`metrics` are in sample. They are the metrics of the cover at `parameters` (design) or of the fixed cover (evaluate), on the case's sample, for the quantity the objective sees: the asset's loss and payout, or in joint cases the sums over the assets. A value is null where ADR 0005 §6 says the metric is undefined.

**Quantiles on a step.** With equally likely draws, a level such as β = 0.9 often falls exactly on a step of the distribution (0.9 · 160 = 144 draws). A floating-point sum of the probabilities can then land on either side of it, so the quantile is either of the two neighbouring atoms. Such a metric is written `{"either": [lower, upper]}`, and either value passes. ADR 0005 §6's rule (a tolerance of 1e-10 on the cumulative probability) gives the lower one. This applies to the VaR columns `var_*_b<β>` and to the return-period columns `*_rp<T>`. CVaR does not depend on the atom and is always a single value.

## How to compare

The scale of a case is the largest summed loss of a draw: `max(sum(row) for row in sample["loss"])`. It is the core's scaling of the design problem and the module's (ADR 0005 §5.3).

**Evaluate cases.** Evaluate the fixed cover on the sample with `pricing`, and compare `premium` and every column of `metrics`.

**Design cases.** Design the template (`cover`) on the sample with `objective`, `pricing` and `budget` (individual cases: `design`; joint cases: Phase 2's `design_joint`). Then:

1. Compare `objective_value`.
2. Compare the parameters as `compare_parameters` says:
   - `"exact"`: every level not in `unidentified` agrees within `tolerances.parameters` times the scale. The unidentified levels are left out: they change nothing on the sample, so any value the constraints allow is optimal.
   - `"within_ranges"`: the module ranges the optimal set (ADR 0005 §5.4, `DesignOptions(ranges=True)`), and every level of `expected.parameters` not in `unidentified` lies within the module's range, widened by `tolerances.parameters` times the scale.
   - `"none"`: the parameters are not compared.
3. Compare `premium` and `metrics`:
   - if `unique` is true, those of the module's designed cover;
   - otherwise, those of the template resolved with `expected.parameters` (`Cover.with_values`), evaluated on the sample. On a non-unique optimum only the objective value is the same for every optimal design. The premium and the metrics depend on which member of the optimal set a solver returns.
4. The module's own `unique` flag may be false where `unique` is true here, because its near-optimal tolerance is looser (1e-6 of the optimum, ADR 0005 §5.4; see "How `compare_parameters` and `unique` were decided"). It must not be true where `unique` is false here.

**Tolerances.**

| Value | Passes if |
|---|---|
| `objective_value` | within `tolerances.objective_value` relative; absolute floor 1e-9 times the scale (the scale squared for MSE) |
| `premium` | within `tolerances.premium` relative; absolute floor 1e-9 times the scale |
| a metric | within `tolerances.metrics` relative; absolute floor 1e-9 times the scale for metrics in loss units, 1e-9 for the unitless ones (`coverage_ratio`, `payout_to_loss_ratio`, `correlation`, `tail_coverage_*`, `cvar_uncovered_to_loss_*`, `false_negative_rate_*`, `false_positive_rate_*`) |
| a parameter | within `tolerances.parameters` times the scale, absolute |

The floors matter near zero. A solver's levels are exact only to rounding: a level equal to a loss in exact arithmetic leaves an uncovered loss of a few units in the last place, not 0.

## How `compare_parameters` and `unique` were decided

- **LPs** (expected uncovered loss, weighted CVaR). The core solves the problem with HiGHS (simplex, a vertex). Then every identified level is ranged twice: its smallest and largest value over the feasible designs whose objective is within ε · max(1, |optimum|) of the optimum, in scaled units, for ε = 1e-9 and for ε = 1e-11 (HiGHS, two LPs per level and ε).
  - At a unique optimum a range is only the tolerance over the objective's slope, so it shrinks a hundredfold from the first ε to the second. On a set of optimal designs it keeps the set's width.
  - A level is pinned when its range shrinks to at most half, or is narrower than 1e-7 of the scale. `unique` is true when every identified level is pinned. In these cases the pinned ranges shrank to 1 % or less, and the others did not shrink (they are at least 2e-3 of the scale wide).
  - A unique optimum is written as HiGHS's vertex, after a check that Clarabel at tight tolerances finds the same levels within 1e-6 of the scale. `compare_parameters` is `"exact"`.
  - Otherwise the solution written is Clarabel's at tight tolerances, an interior point of the optimal set. It is checked to lie within the ranges, and `compare_parameters` is `"within_ranges"`.
- **QPs** (MSE). The core solves the problem with Clarabel at tight tolerances. `unique` follows ADR 0005 §5.4's rule for the MSE route: H = Bᵀ diag(p) B, over the identified levels, is positive definite (smallest eigenvalue above 1e-10 times the largest). In individual cases H is diagonal, so the identified levels are always unique and `compare_parameters` is `"exact"`. In joint cases H can be singular, when two assets' bins hold the same draws; then `compare_parameters` is `"none"`, because the MSE route computes no ranges.

## The cases

| Family | Cases | `kind`, `source` |
|---|---|---|
| Step designs | {MSE, expected uncovered, weighted CVaR at β 0.9 and 0.99} × {pure, cost of capital} × {individual, joint} × {synthetic, thesis}: 32 | design, core |
| Fixed step covers | {pure, cost of capital} × {synthetic, thesis}, asset A1: 4 | evaluate, core |
| Fixed linear covers | upper tail {pure, cost of capital}, lower tail {pure}: 3 | evaluate, closed_form |

Every design case has `budget` 0.8 and weighted-CVaR weight α 0.9. The core cases' cost-of-capital pricing is rate 0.06 at q 0.99; the closed-form one is rate 0.1 at q 0.9. Individual cases use the data set's first asset.

### Data sets

- **`synthetic`**: 150 years, assets A1, A2, A3 (values 10, 6 and 3 million USD), from `numpy.random.default_rng(20261105)`. Each year has a storm with probability 0.7. A storm has an intensity 22 + Gamma(2, 7) m/s, and the hazard at each asset adds N(0, 3). The loss is the asset's value times the damage ratio v³ / (1 + v³), v = max(h − 25.7, 0) / 49, of the hazard h. The index is the hazard plus another N(0, 3), floored at 0, so index and loss differ (basis risk). Indices are rounded to 0.01 m/s and losses to whole USD. Three indices of A1 sit exactly on breakpoints (25, 36 and 60), to test the bin rule. Step breakpoints 25, 30, 36, 43, 51, 60 m/s.
- **`thesis`**: 160 years of the parity fixture (IRIS storms at 9 Miami assets, wind at the asset in m/s, loss in USD), assets A1, A2 and A9 (the three of largest value). In year order: the first 100 years with exactly one event row and a loss at one of the three assets at least; the first 30 years with exactly one event row and no loss at them; and the first 30 years without an event row. Years with several event rows are never taken, because the module has one draw per year (ADR 0005 §8). Index and loss are the fixture's values as stored; the periods are the fixture's years (0-based). No noise layer. Step breakpoints 30, 35, …, 60 m/s.
- **`handmade`**: 20 years, 2001–2020, chosen by hand with round values. Upper tail: the index `rx1day` (mm/day), loss in EUR, cover attachment 50, exhaustion 150, limit 1000. Lower tail: the index `spei3` (unitless), loss in EUR, attachment −1, exhaustion −3, limit 800.

### Core settings (ADR 0005 §8)

- The core's `StepPayout(..., below_attachment="zero")`: nothing below the first breakpoint.
- The annual basis, with one draw per year.
- At most one event row per year. The core sees no row for a year without an event and pools it into one zero-loss outcome; that gives the same values as a draw with index 0 and loss 0.
- The core's `Budget(0.8)`, `WeightedCVaR(alpha=0.9, beta)`, `PurePremium()` and `CostOfCapitalLoad(rate=0.06, q=0.99)`, in the scopes `Individual()` and `Portfolio()`.
- Solvers, through the core's `solve.solve` with these policies: HiGHS for the LP vertices and the ranging LPs; Clarabel with `tol_gap_abs`, `tol_gap_rel` and `tol_feas` at 1e-12 for the QPs and the non-unique LPs; OSQP at `eps` 1e-12 to check the QPs (agreement 1e-9). The core's default policy is run too, as a check (agreement 1e-5). Its OSQP, at `eps` 1e-8, meets a binding budget only to about 1e-6 relative, which moves the MSE objective by up to about 1.5e-6 relative: more than the cases' tolerance, so its solutions are not written.
- Levels within 1e-9 of the scale of zero are written as 0 (ADR 0005 §5.3's rule). Computed values are rounded to 12 significant digits; inputs are written as stored.

### Metrics

ADR 0005 §6's column names, with its `MetricOptions` defaults: β ∈ {0.9, 0.95, 0.99}, return periods T ∈ {2, 5, 10, 25, 50, 100, 250} years, loss threshold 0 and payout threshold 0. Labels follow crc-sdk's rule: 0.99 gives `b0_99`, 100 gives `rp100`, 0 gives `l0`.

The core cases carry the metrics the core computes. The script recomputes the plain ones and the quantile atoms from the draws and requires agreement to 1e-12, so the draws and the core's outcomes match.

| Columns | Core function |
|---|---|
| `expected_loss`, `expected_payout`, `expected_uncovered`, `payout_to_loss_ratio`, `correlation` | `evaluate.kpis`, the KPIs of the same names |
| `rmse` | `evaluate.kpis`, `rmse_residual` |
| `premium` | `evaluate.kpis`, `premium` (`pricing.premium_value`) |
| `var_uncovered_b<β>`, `cvar_uncovered_b<β>` | `evaluate.kpis` at β |
| `var_loss_b<β>`, `cvar_loss_b<β>` | `riskmeasures.var_cvar` of the loss |
| `var_net_loss_b<β>`, `cvar_net_loss_b<β>` | `riskmeasures.var_cvar` of loss − payout + premium |
| `loss_rp<T>`, `payout_rp<T>`, `uncovered_rp<T>` | `evaluate.exceedance_curves`, the AEP curves |
| `net_loss_rp<T>` | `riskmeasures.lower_quantile` of loss − payout + premium |

The closed-form cases carry every column of ADR 0005 §6. The new metrics (`coverage_ratio`, `tail_coverage_b<β>`, `cvar_uncovered_to_loss_b<β>`, `false_negative_rate_l<ℓ>`, `false_positive_rate_l<ℓ>`) are only there. The script computes them in exact rational arithmetic; the columns that are also core quantities must agree with the core's risk measures to 1e-12.

## Where the format goes beyond the ADR 0005 draft

§8 doesn't settle these points; the cases do the following.

1. **Array orientation.** §8's example writes `"index": [[...]]`. Here `index` and `loss` are `(n, n_assets)`, one row per draw, as in §4.1.
2. **Joint cases.** §8 has one `cover` and flat `parameters`. Here a joint case has a list of covers and `parameters` and `unidentified` keyed by asset id, and its metrics are of the sums over the assets.
3. **The core's cap.** The core caps every level at the asset's largest loss. Here that is the `Free` upper bound, and `limit` is null, as in §8's example.
4. **Premium and metrics of a non-unique design** are compared through `expected.parameters` (step 3 of "How to compare"), not against the module's design.
5. **The floor "1e-9 absolute near zero"** of §8 is taken as 1e-9 times the scale for values in loss units.
6. **`"exact"` with unidentified levels.** MSE designs are unique on their identified levels; `"exact"` leaves the unidentified ones out.
